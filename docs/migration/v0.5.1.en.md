# Migrating to v0.5.1

v0.5.1 corrects lifecycle, broker delivery, response commit ordering, and WebSocket authentication boundaries introduced or exposed in v0.5.0. Do not move the existing `v0.5.0` tag; update applications to `v0.5.1`.

## HTTP responses and transactions

A success response is now prepared in memory. JSON serialization, cookie and status validation, return-value handling, and `PostHandle` finish before `BeforeResponse` runs. The prepared response is flushed to the real HTTP writer only after every `BeforeResponse` succeeds. Preparation failures reach `BeforeResponse`, allowing a request transaction to roll back.

Domain-event post-processing also runs only after response serialization and cookie/status validation succeed. A request whose response cannot be prepared therefore cannot publish an external event first.

```go
func (i *TxInterceptor) BeforeResponse(
	ctx core.ExecutionContext,
	meta core.HandlerMeta,
	executionErr error,
) error {
	if executionErr != nil {
		return i.tx.Rollback()
	}
	return i.tx.Commit()
}
```

Neither a physical socket write nor a broker publish can be atomic with a database commit. Use a transactional outbox and idempotency keys when the event publish and a later `BeforeResponse` commit failure must resolve as one atomic outcome.

## Kafka failure and shutdown

- A NACK or offset commit failure invalidates the current reader. No later message is read before the reader is rebuilt, preventing a higher offset in the same partition from committing past the failed message.
- `ConsumerRetry` now applies both to the initial reader build and to reader reconstruction after a failed ACK/NACK. This bounds immediate consumer-group rejoin loops caused by a permanently failing message.
- `Stop()` and `Done()` complete only after the handler, ACK/NACK, and reader close have drained.

Kafka handlers must remain idempotent because redelivery is possible. The built-in runtime does not automatically skip or dead-letter a permanently failing message, so its partition can remain blocked until the message or handler is repaired.

## RabbitMQ publisher and consumer

The RabbitMQ publisher uses persistent messages, `mandatory=true`, and publisher confirms. An unroutable `basic.return` or a negative/missing confirm is not success. `PublisherRetry` controls both the initial connection and reconnects after a broken connection.

```go
RabbitMQ: &boot.RabbitMqOptions{
	URL: "amqps://user:pass@rabbit.example/vhost",
	PublisherRetry: boot.PublisherRetryOptions{
		InitialDelay:   200 * time.Millisecond,
		MaxDelay:       5 * time.Second,
		MaxAttempts:    5,
		ConfirmTimeout: 5 * time.Second,
	},
	Read: &boot.RabbitMqReadOptions{
		Exchange:      "events",
		PrefetchCount: 16,
	},
	Write: &boot.RabbitMqWriteOptions{Exchange: "events"},
}
```

A zero `PrefetchCount` uses the safe default of 1. A lost confirm can cause a retry after the broker accepted the first publish, so consumers must be idempotent.

## WebSocket handshake authentication

An interceptor that protects a WebSocket endpoint should also implement the optional `core.WebSocketHandshakeInterceptor`. A connection slot is reserved before `PreHandshake`, and `PreHandshake` still runs before the HTTP upgrade. Unauthenticated handshake work therefore counts against `MaxConnections`. Message-level `PreHandle` keeps its existing behavior.

```go
func (i *AuthInterceptor) PreHandshake(
	ctx core.WebSocketHandshakeContext,
	meta core.HandlerMeta,
) error {
	token := ctx.Header("Authorization")
	if token == "" {
		return httperr.Unauthorized("missing credentials")
	}
	return i.verify(token)
}
```

`WebSocketHandshakeContext` and the message-stage `core.WebSocketMessageContext` expose immutable snapshots of handshake headers, query values, cookies, remote address, host, and request URI. Only implementations registered with `App.InterceptorFor(boot.InterceptorWebSocket, auth)` or on the route participate in the handshake phase.

## Bootstrap and validation

- The HTTP listener starts only after controller/consumer warm-up, an actual Kafka protocol handshake, RabbitMQ topology connection validation, and custom transport initialization succeed. `ConsumerRetry` also applies to this startup readiness check.
- If custom transport initialization fails part-way through, initialized transports stop in reverse order.
- A negative `ShutdownTimeout` is a `SHUTDOWN_TIMEOUT_INVALID` configuration error.
- `Run` does not return until consumer workers and transports finish stopping.

## DI, router, and resolver behavior

- Nil constructors and nil pointer/interface/function/channel provider results produce explicit DI errors. Nil slice/map providers remain valid representations of an empty collection.
- Resolving one provider through an interface or its concrete type shares one singleton.
- A static route dead end backtracks to a valid parameter route.
- Named `string`/`[]byte` and extended `ControllerContext` types use safe assignability/convertibility rules and return an error instead of panicking when unsupported.

## Duplicate interceptors

This documents the v0.5.0 behavior: the same pointer instance merges scopes and executes once; different pointers of the same type execute independently. Typed-nil placeholders share the container singleton, while value registrations remain independent.
