# v0.5 보안 기본값 마이그레이션

> v0.5.0의 수명주기 및 전달 보정은 [v0.5.1 마이그레이션 안내서](v0.5.1.md)를 함께 확인하십시오. 기존 v0.5.0 태그는 이동하지 않습니다.

v0.5는 브로커 전송, WebSocket, CORS, 컨슈머 실패 처리, 쿠키 직렬화의 보안 기본값을 강화합니다. 기존 설정을 그대로 사용하면 시작 단계의 명시적 검증 오류 또는 런타임 동작 변화가 발생할 수 있습니다.

## 인터셉터 응답 전 생명주기

`core.Interceptor`에 응답 전 실행되는 `BeforeResponse`가 추가되었습니다. 알파 버전 계약 변경이므로 모든 인터셉터 구현은 이 메서드를 구현해야 합니다.

```go
BeforeResponse(
    ctx core.ExecutionContext,
    meta core.HandlerMeta,
    executionErr error,
) error
```

파이프라인은 컨트롤러가 반환한 `error`와 실행 후 훅 오류를 `executionErr`로 보존하고, `PreHandle`을 성공한 라우트 인터셉터와 전역 인터셉터의 `BeforeResponse`를 각각 역순으로 실행합니다. 여기서 반환된 오류도 최종 오류에 포함합니다. 성공 응답은 모든 `BeforeResponse`가 성공한 뒤에만 기록됩니다.

요청 단위 트랜잭션은 `PreHandle`에서 시작하고 `BeforeResponse`에서 커밋하거나 롤백하십시오. `AfterCompletion`은 응답 처리 후 로깅과 정리 용도로 사용합니다.

```go
func (i *TxInterceptor) BeforeResponse(
    ctx core.ExecutionContext,
    meta core.HandlerMeta,
    executionErr error,
) error {
    tx, ok := transactionFrom(ctx)
    if !ok {
        return nil
    }
    if executionErr != nil {
        return tx.Rollback()
    }
    return tx.Commit()
}
```

애플리케이션을 실행하지 않고 전체 설정 문제를 먼저 확인할 수 있습니다.

```go
if err := app.Validate(options); err != nil {
    log.Fatal(err)
}
```

`Run`도 같은 사전 검증을 네트워크 연결 전에 자동 수행합니다. 오류는 `*boot.ConfigError`이며 각 `ConfigIssue`에 `Path`, `Code`, `Message`, `Hint`가 포함됩니다. URL 자격 증명은 오류에 포함하지 않습니다.

## Kafka

운영 환경에서는 별도 설정 없이 Spine이 TLS 1.2 이상 설정을 컨슈머와 퍼블리셔에 적용합니다.

```go
Kafka: &boot.KafkaOptions{
    Brokers: []string{"kafka.example:9093"},
    Read:  &boot.KafkaReadOptions{GroupID: "orders"},
    Write: &boot.KafkaWriteOptions{},
}
```

사용자 정의 CA, mTLS 또는 고급 SASL/연결 설정이 필요한 경우에만 `TLS`, `Dialer`, `Transport`를 재정의합니다. 명시적 TLS 설정과 `AllowInsecureTransport`를 동시에 설정하면 사전 검증이 실패합니다.

격리된 로컬 개발 환경에서만 평문을 명시적으로 허용하십시오.

```go
Kafka: &boot.KafkaOptions{
    Brokers:                []string{"localhost:9092"},
    AllowInsecureTransport: true,
    Read:                   &boot.KafkaReadOptions{GroupID: "local"},
}
```

## RabbitMQ

기본 URL은 `amqps://`여야 합니다. 로컬 `amqp://`는 `AllowInsecureTransport: true`가 필요합니다.

```go
Read: &boot.RabbitMqReadOptions{
    Exchange:      "events",
    FailurePolicy: boot.RabbitMqFailureReject,
    DeadLetter: &boot.RabbitMqDeadLetterOptions{
        Exchange:   "events.dlx",
        RoutingKey: "events.failed",
    },
}
```

v0.4.3 RabbitMQ 컨슈머는 핸들러 실패를 항상 `NACK(requeue=true)`로 처리했으며, 당시 `RabbitMqReadOptions`에는 `RequeueOnError` 필드가 없었습니다. v0.4.3과 동일한 재큐잉 동작을 유지하려면 v0.5에서 다음과 같이 명시적으로 설정하십시오.

```go
FailurePolicy: boot.RabbitMqFailureRequeue,
```

이 호환 설정은 처리 불가능한 메시지를 무한히 재전달할 수 있습니다. v0.5 신규 배포에서는 위 예제처럼 `RabbitMqFailureReject`와 DLX를 함께 설정하는 방식을 권장합니다. 거부된 메시지는 DLX가 구성된 큐에서는 데드 레터로 전달되지만, DLX가 없으면 브로커가 폐기할 수 있습니다. DLX 교환기는 운영자가 미리 생성해야 하며, 기존 큐의 인자가 다르면 RabbitMQ가 큐 사전 조건 오류를 반환할 수 있으므로 배포 전에 토폴로지를 맞추십시오. v0.5의 `RequeueOnError` 필드는 임시 호환 경로로만 제공되며 사용 중단 예정입니다. 새 코드는 `FailurePolicy`를 사용하십시오.

RabbitMQ 디스패치 키는 AMQP `Type`이 아니라 큐 바인딩의 `RoutingKey`입니다. 외부 퍼블리셔가 두 값을 다르게 보냈다면 컨슈머 등록 이름과 라우팅 키를 맞춰야 합니다.

## 컨슈머 전송 재시도

리더 오류가 발생하면 Spine은 기존 리더를 닫고 백오프와 지터를 적용한 뒤 새 리더를 생성합니다. 이 정책은 핸들러 실패의 ACK/NACK 정책과 별개입니다.

```go
ConsumerRetry: boot.ConsumerRetryOptions{
    InitialDelay: 200 * time.Millisecond,
    MaxDelay:     10 * time.Second,
    Multiplier:   2,
    Jitter:       0.2,
    MaxAttempts:  20,
},
```

값을 별도로 지정하지 않으면 최초 지연 100ms, 최대 지연 5초, 배수 2, 지터 20%, 무제한 재시도를 사용합니다.

## 전역 인터셉터 범위

기존 `app.Interceptor(...)`는 보안상 HTTP와 WebSocket 모두에 적용됩니다. HTTP 전용 가정이 있는 인터셉터는 범위를 명시하십시오.

```go
app.InterceptorFor(boot.InterceptorAll, auth)
app.InterceptorFor(boot.InterceptorHTTP, corsInterceptor)
app.InterceptorFor(boot.InterceptorWebSocket, wsRateLimiter)
```

외부에서 `spine.App` 인터페이스를 직접 구현했다면 새 `Validate`와 `InterceptorFor` 메서드를 구현해야 합니다.

### 동일 인터셉터의 중복 등록

v0.5의 전역 인터셉터 병합은 구체 타입만으로 중복을 제거하지 않습니다.

- 같은 포인터 인스턴스를 여러 scope에 등록하면 한 인스턴스로 병합되고 scope만 합쳐집니다.
- 같은 타입이어도 서로 다른 포인터 인스턴스는 각각 독립적으로 실행됩니다.
- DI 생성을 요청하는 동일 타입의 typed-nil placeholder는 하나로 병합되고 컨테이너의 singleton을 공유합니다.
- 값 타입 인터셉터는 등록마다 독립적으로 실행됩니다.

따라서 같은 상태를 공유하려면 같은 포인터를 재사용하고, 같은 타입의 독립된 정책을 실행하려면 서로 다른 인스턴스를 등록하십시오.

## WebSocket 출처와 연결 용량

명시적 출처 목록을 권장합니다.

```go
WebSocket: boot.WebSocketOptions{
    AllowedOrigins: []string{"https://app.example.com"},
    MaxConnections: 4096,
}
```

출처 목록이 비어 있으면 프로토콜과 호스트가 모두 같은 요청만 허용됩니다. TLS 종료 프록시 뒤에서는 `TrustedProxyCIDRs`를 지정할 수 있습니다. `Forwarded`와 `X-Forwarded-Proto`는 요청 상대가 이 목록에 포함될 때만 사용됩니다. 프록시는 외부에서 들어온 전달 헤더를 제거하거나 덮어써야 합니다.

동시 연결 기본값은 `boot.DefaultWebSocketMaxConnections`(1024)입니다. 제한 해제는 `boot.UnlimitedWebSocketConnections`를 사용합니다. 상한 초과 요청은 업그레이드되지 않고 HTTP 503, `Retry-After`, `WEBSOCKET_CAPACITY_EXCEEDED` JSON 응답을 받습니다.

## CORS

`AllowOrigins: []string{"*"}`와 `AllowCredentials: true` 조합은 더 이상 조용히 보정되지 않습니다. 시작 단계에서 검증하려면 다음 생성자를 사용하십시오.

```go
corsInterceptor, err := cors.NewValidated(cors.Config{
    AllowOrigins:     []string{"https://app.example.com"},
    AllowCredentials: true,
})
```

기존 `cors.New`는 소스 호환되지만 잘못된 설정은 첫 요청의 헤더 기록 전에 구조화된 오류를 반환합니다.

## 쿠키

쿠키 이름, 값, 경로, 도메인, SameSite, Priority가 유효하지 않으면 JSON/문자열/바이너리/리다이렉트 핸들러는 헤더나 본문을 쓰기 전에 오류를 반환합니다. 문자를 조용히 삭제하지 않습니다.

유니코드, 공백, 구분자 또는 임의 바이트를 값으로 왕복해야 할 때만 명시적으로 base64url 인코딩하십시오.

```go
encoded := httpx.EncodeCookieValue("사용자 입력; arbitrary value 🍪")
raw, err := httpx.DecodeCookieValue(encoded)
```

JWT처럼 이미 쿠키에 안전한 값은 다시 인코딩할 필요가 없습니다.

전체 설정 예제는 [`examples/security-config/main.go`](../../examples/security-config/main.go)를 참고하십시오.
