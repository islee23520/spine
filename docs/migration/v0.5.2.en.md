# Migrating to v0.5.2

v0.5.2 corrects request rejection timing, client-input errors, and route and consumer registration validation. Public API usage remains compatible, while invalid requests and configurations now fail earlier and more explicitly.

## Request execution order

Route `Interceptor.PreHandle` now runs before DTO, form, multipart, and path argument resolution. An unauthorized request does not start request-body resolution. Interceptors should not depend on resolved controller arguments.

Malformed JSON, form, multipart, `path.Int`, and `path.Boolean` inputs now return HTTP 400. Requests exceeding `MaxBodyBytes` continue to return HTTP 413.

## Startup validation

`App.Validate` reports nil or invalid HTTP route handlers at `Routes[n].Handler`. This moves reflection failures from runtime startup into deployment preflight.

Registering the same consumer topic twice now returns an error from `Consumers().Register`. Consumer routing currently supports one handler per topic, so applications should continue checking every registration error.

## CORS and cookies

The CORS interceptor responds with 204 only to actual preflight requests containing both `Origin` and `Access-Control-Request-Method`. Ordinary `OPTIONS` requests continue to their registered route handler.

Deletion cookies now use `Max-Age=0` with a past `Expires` value and serialize HTTP dates in GMT. Cookie deletion API usage is unchanged.

## Context-driven shutdown

`App.RunContext(ctx, options)` is now available. Existing `App.Run(options)` calls remain valid; use `RunContext` when a test or service host should trigger graceful shutdown by cancelling a context instead of sending a process signal.
