# v0.5.1 마이그레이션

v0.5.1은 v0.5.0의 수명주기, 브로커 전달, 응답 커밋 순서, WebSocket 인증 경계를 보정하는 패치 릴리스입니다. 기존 `v0.5.0` 태그를 이동하지 말고 애플리케이션 의존성을 `v0.5.1`로 올리십시오.

## HTTP 응답과 트랜잭션

성공 응답은 메모리에서 먼저 준비됩니다. JSON 직렬화, 쿠키 검증, status 검증, 반환값 처리와 `PostHandle`이 모두 끝난 다음 `BeforeResponse`가 호출되고, 성공한 경우에만 실제 HTTP writer로 flush됩니다. 응답 준비가 실패하면 `BeforeResponse`는 해당 오류를 받아 트랜잭션을 롤백할 수 있습니다.

domain-event 후처리도 응답 직렬화·쿠키·status 검증이 성공한 뒤에만 실행됩니다. 따라서 응답을 만들 수 없는 요청이 외부 이벤트를 먼저 발행하는 경로는 차단됩니다.

```go
func (i *TxInterceptor) BeforeResponse(
	ctx core.ExecutionContext,
	meta core.HandlerMeta,
	executionErr error,
) error {
	if executionErr != nil {
		return i.tx.Rollback()
	}
	return i.tx.Commit()
}
```

실제 소켓 쓰기뿐 아니라 브로커 publish도 데이터베이스 커밋과 원자적으로 묶을 수 없습니다. 이벤트 publish 뒤 `BeforeResponse` 커밋이 실패하는 경우까지 하나의 원자적 결과로 보장해야 한다면 트랜잭셔널 outbox와 멱등 키를 함께 사용하십시오.

## Kafka 소비 실패와 종료

- NACK 또는 offset commit 실패가 발생하면 현재 reader를 폐기하고 재생성하기 전에는 다음 메시지를 읽지 않습니다. 같은 partition의 높은 offset이 실패 메시지를 건너뛰어 커밋되는 경로를 차단합니다.
- 최초 reader 생성 실패뿐 아니라 실패한 ACK/NACK 뒤 reader를 재생성할 때도 `ConsumerRetry`가 적용됩니다. 영구적으로 실패하는 메시지가 즉시 consumer group 재가입을 반복하는 경로를 제한합니다.
- `Stop()`과 `Done()`은 handler, ACK/NACK, reader 종료가 모두 끝난 뒤에만 완료됩니다.

Kafka handler는 재전달될 수 있으므로 멱등해야 합니다. 내장 런타임은 영구 실패 메시지를 자동으로 건너뛰거나 DLQ로 보내지 않으므로, 해당 메시지가 해결될 때까지 partition 진행이 멈출 수 있습니다.

## RabbitMQ publisher와 consumer

RabbitMQ publisher는 persistent 메시지, `mandatory=true`, publisher confirm을 사용합니다. 라우팅 불가(`basic.return`) 또는 negative/missing confirm은 성공으로 처리하지 않습니다. 최초 연결 및 연결 단절 이후 재연결은 `PublisherRetry`로 제어합니다.

```go
RabbitMQ: &boot.RabbitMqOptions{
	URL: "amqps://user:pass@rabbit.example/vhost",
	PublisherRetry: boot.PublisherRetryOptions{
		InitialDelay:   200 * time.Millisecond,
		MaxDelay:       5 * time.Second,
		MaxAttempts:    5,
		ConfirmTimeout: 5 * time.Second,
	},
	Read: &boot.RabbitMqReadOptions{
		Exchange:      "events",
		PrefetchCount: 16,
	},
	Write: &boot.RabbitMqWriteOptions{Exchange: "events"},
}
```

`PrefetchCount`의 0 값은 안전한 기본값 1입니다. publish confirm이 유실되면 재시도로 중복이 발생할 수 있으므로 consumer는 멱등해야 합니다.

## WebSocket handshake 인증

인증이 필요한 WebSocket 인터셉터는 선택적 `core.WebSocketHandshakeInterceptor`도 구현하십시오. 연결 슬롯은 `PreHandshake` 전에 예약되고, `PreHandshake`는 HTTP upgrade 전에 실행됩니다. 따라서 인증되지 않은 handshake 작업도 `MaxConnections` 한도에 포함되며, 메시지별 `PreHandle`은 기존대로 유지됩니다.

```go
func (i *AuthInterceptor) PreHandshake(
	ctx core.WebSocketHandshakeContext,
	meta core.HandlerMeta,
) error {
	token := ctx.Header("Authorization")
	if token == "" {
		return httperr.Unauthorized("missing credentials")
	}
	return i.verify(token)
}
```

`WebSocketHandshakeContext`와 메시지 단계의 `core.WebSocketMessageContext`는 handshake header, query, cookie, remote address, host와 request URI의 불변 snapshot을 제공합니다. `App.InterceptorFor(boot.InterceptorWebSocket, auth)` 또는 route interceptor로 등록한 구현만 handshake 단계에 참여합니다.

## Bootstrap과 설정 검증

- HTTP listener는 controller/consumer warm-up, Kafka 실제 protocol handshake, RabbitMQ topology 연결 검증, custom transport 초기화가 모두 성공한 뒤 시작합니다. 이 startup readiness에도 `ConsumerRetry`가 적용됩니다.
- custom transport 초기화가 중간에 실패하면 이미 초기화된 transport를 역순으로 중지합니다.
- 음수 `ShutdownTimeout`은 `SHUTDOWN_TIMEOUT_INVALID` 설정 오류입니다.
- `Run` 반환은 consumer worker와 transport 종료가 끝난 뒤입니다.

## DI, router, resolver

- nil constructor와 nil pointer/interface/function/channel provider 결과는 명시적 DI 오류입니다. 비어 있음을 정상적으로 표현하는 nil slice/map provider는 허용됩니다.
- interface와 concrete 타입으로 같은 provider를 resolve해도 하나의 singleton을 공유합니다.
- 정적 route가 하위에서 막히면 parameter route로 backtrack합니다.
- named `string`/`[]byte`와 확장 `ControllerContext` 타입은 안전한 assignability/convertibility 규칙으로 처리되며 지원할 수 없으면 panic 대신 오류를 반환합니다.

## 인터셉터 중복 등록

v0.5.0에서 도입된 의미를 명시합니다. 같은 포인터 인스턴스는 scope가 병합되어 한 번 실행되고, 같은 타입의 서로 다른 포인터 인스턴스는 각각 실행됩니다. typed-nil placeholder는 같은 container singleton을 공유하며 값 타입 등록은 독립적입니다.
